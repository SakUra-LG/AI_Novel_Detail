# 一般生成说明

## 文档用途
这份文档用于说明当前项目中“神话故事改写长篇版”的一般生成方式、运行步骤、生成目标和使用注意事项。

当前版本重点面向：
- 中国神话故事改写
- 偏《哪吒魔童降世》式的幽默与人物互怼风格
- 结尾带感动收束
- 适配约 10 分钟视频创作的长篇文本

---

## 环境准备
运行前请先确保当前 Python 已安装依赖。

推荐在项目目录执行：

```bash
python -m pip install -r requirements.txt
```

如果机器上有多套 Python，建议先确认当前解释器：

```bash
python -c "import sys; print(sys.executable)"
```

如果运行 `python main.py` 时出现：

- `No module named 'dashscope'`
- `No module named 'torch'`
- `No module named 'transformers'`
- `No module named 'sklearn'`

通常说明当前终端使用的不是你安装依赖时的那套 Python，需要重新对当前解释器安装依赖。

---

## 当前版本的核心目标
当前版本不再只追求“能生成一篇神话改写”，而是重点追求以下四件事同时成立：

1. 篇幅足够长  
   目标总字数约为 `6000~8000` 字，适配 10 分钟左右的视频改编需求。

2. 风格稳定  
   整体保持偏幽默、偏人物性格驱动的表达方式，不写成纯严肃史诗，也不写成纯搞笑段子。

3. 主线不跑偏  
   保留原神话的关键事件链、因果关系和最终结局，不允许扩写时偏离核心神话。

4. 结尾有感动收束  
   前半段以幽默、互怼、动作推进为主，后半段特别是第三幕结尾，逐步转入情感回收和感动落点。

## 一般生成流程

### 1. 初始化知识库
首次使用项目，或更新了样本库、专业知识库后，需要先重新初始化向量文件。

运行：

```bash
python Handle_Content.py
python Handle_Profession.py
```

作用：
- `Handle_Content.py`：处理 `knowledgeBase/Content.txt` 中的素材文本，生成内容向量与结构化内容文件。
- `Handle_Profession.py`：处理 `knowledgeBase/Professional.txt` 中的专业知识，生成专业知识向量与元数据文件。

如果只是日常生成，且知识库没有改动，这一步可以跳过。

---

### 2. 运行主程序
在项目目录下运行：

```bash
python main.py
```

程序会提示输入问题，例如：

```text
改写后羿射日的故事，要偏幽默，人物互动多一些，结尾感人，适合改成十分钟视频
```

---

### 3. 自动识别神话改写需求
当输入里包含神话相关关键词时，程序会自动进入“神话改写长篇流程”。

常见触发词包括：
- 神话
- 盘古
- 女娲
- 后羿
- 嫦娥
- 哪吒
- 大禹
- 共工
- 精卫
- 夸父
- 牛郎织女
- 山海经

---

### 4. 长篇神话改写的内部流程
当前版本不是“一次性直接生成全文”，而是使用多阶段工作流：

1. 检索相关样本  
   从知识库中检索与当前神话最相近的内容样本，优先参考“神话重写·哪吒风格”类样本。

2. 生成总体大纲  
   先产出完整故事总纲，不只是原神话主线，还允许加入“功能性扩展场景”。

3. 拆分三幕  
   将总体大纲拆分为三幕：
   - 第一幕：背景、动机、出发、筹备
   - 第二幕：核心行动过程
   - 第三幕：结果、余波、情感回收、结尾

4. 生成节拍卡  
   每一幕再拆成多张节拍卡，当前长篇版数量大致为：
   - 第一幕：`6~8` 张
   - 第二幕：`10~12` 张
   - 第三幕：`6~8` 张

5. 逐张节拍卡生成正文  
   不是整幕一次生成，而是每张节拍卡生成一小段，再按顺序拼接成长篇正文。

6. 第三幕单独强化感动收束  
   最后 1~2 张节拍卡会偏重情感回应、代价显形、世界变化和前文伏笔回收。

7. 最终质量检查  
   程序会对篇幅、格式、乱码、跑题风险、结尾完整性做额外检查，不足时会优先重写后段，必要时扩写第二幕。

---

## 当前版本允许的“扩写方式”
为了把文本从中短篇扩展到适合视频改编的长度，当前版本允许加入以下类型的扩展内容：

### 1. 动作扩写
适用于核心动作过程。

例子：
- 后羿如何站定、蓄力、举弓、瞄准、放箭
- 盘古如何举斧、蓄力、挥斧、撑天、踏地
- 女娲如何寻石、炼石、补天

特点：
- 更稳
- 不容易跑题
- 最适合拉长篇幅

### 2. 场景扩写
适用于增加画面感和视频改编空间。

例子：
- 大旱后的村庄状态
- 山顶、荒野、火云、裂地、风声、水汽等环境反应
- 世界逐渐恢复生机后的变化

特点：
- 有助于影视化
- 有助于减轻“只剩动作”的单调感

### 3. 幽默情节扩写
适用于在不破坏主线的前提下增加人物互动。

例子：
- 主角和固定拆台副角互怼
- 紧张场面中的嘴硬式吐槽
- 严肃目标和生活化反应之间的反差

特点：
- 容易保持当前风格
- 比强行新增复杂支线更稳

### 4. 功能性新情节
允许新增，但必须非常克制。

只能用于：
- 推动主线决策
- 说明行动代价
- 加强人物关系
- 埋结尾伏笔
- 展示行动前后余波

不能用于：
- 开新世界观
- 加新主线
- 写与神话主题无关的日常段子
- 为了凑字数加入无关人物和无关事件

## 当前版本的推荐使用方式

### 推荐写法
输入时尽量直接说明以下几点：

1. 要改写哪个神话  
2. 希望偏幽默还是偏庄重  
3. 是否需要更强的人物互动  
4. 是否强调动作描写  
5. 是否要更感人的结尾  
6. 是否明确要求适合十分钟视频

例如：

```text
改写后羿射日的故事，整体偏幽默，师徒互怼要多一些，动作描写详细，结尾要有感动收束，适合十分钟视频
```

或：

```text
改写盘古开天地，保持史诗感，但前半段要有轻微幽默，动作拆解要细，结尾要感人，篇幅适合十分钟视频
```

## 输出内容的典型特点
当前长篇版正常情况下会表现出以下特征：

- 明显比旧版更长
- 不再只靠三幕粗略展开，而是通过更多节拍卡细分过程
- 会加入筹备、路途、试探、余波等功能性场景
- 第二幕会明显更厚，承担主要动作过程和冲突过程
- 第三幕不会仓促结束，会尽量保留余波、关系回收和情感落点

---

## 当前版本重点防止的问题
为了避免长篇生成时常见的质量问题，当前版本专门在流程和后处理里防以下情况：

### 1. 为凑字数写废话
解决方式：
- 扩写内容必须来自节拍卡
- 只允许功能性扩展场景
- 过程必须服务主线

### 2. 写到后面跑题
解决方式：
- 节拍卡必须和大纲顺序对齐
- 每小节都校验是否命中当前节拍关键词

### 3. 出现乱码、英文、繁体混杂、奇怪符号
解决方式：
- 后处理会清掉明显英文污染
- 最终质量校验会检测明显乱码和异常格式

### 4. 结尾崩掉或突然结束
解决方式：
- 第三幕后半段单独采用偏感动收束的提示策略
- 结尾不达标时优先重写第三幕

### 5. 总字数还是不够
解决方式：
- 若总字数不足，程序会优先扩写第二幕，再重新生成第三幕收束

## 生成失败时优先检查什么
如果生成结果仍不理想，建议按以下顺序排查：

### 情况 1：字数仍然偏短
优先检查：
- 输入里是否明确写了“适合十分钟视频”
- 样本库里是否有足够的神话长篇样本
- 第二幕节拍卡是否被生成得过少

### 情况 2：幽默不够
优先检查：
- `knowledgeBase/Content.txt` 中“神话重写·哪吒风格”样本是否足够
- 固定拆台副角是否在大纲里被明确写出
- 输入里是否明确要求“人物互动多一些”“互怼更多一些”

### 情况 3：结尾不够感人
优先检查：
- 第三幕节拍卡是否包含情感伏笔和关系推进
- `touching_ending_examples.txt` 与 `touching_foreshadow_examples.txt` 是否足够有效
- 输入里是否明确写了“结尾要感人”

### 情况 4：内容变长但质量下降
优先处理：
- 少加无关支线
- 多加动作分解、环境反应、人物互动
- 让扩写围绕主线做“纵向展开”，不要“横向乱开”

---

## 当前版本的建议理解
当前版本最稳的思路不是“无限加新剧情”，而是：

- 先保住原神话主线
- 再通过动作分解扩写
- 再通过场景细节扩写
- 再通过人物互怼和关系推进扩写
- 最后通过余波和感动收束补足结尾厚度

也就是说，当前版本更适合：
- 增厚
- 拉长
- 细化
- 强化风格

而不适合：
- 大幅魔改原神话骨架
- 临时加入过多新角色、新势力、新支线

---

## 一句话总结
当前项目的神话改写一般生成方式，可以理解为：

**先用样本和检索确定风格，再用“总纲 -> 三幕 -> 多节拍卡 -> 逐段生成 -> 第三幕感动收束”的长篇工作流，把神话改写稳定扩展到 6000~8000 字左右，同时尽量保住幽默强度、动作细节和结尾质量。**
